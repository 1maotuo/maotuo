Maotuo 整体理解与讲解稿

这份文档的目标不是让你背代码，而是帮助你把已经熟悉的 Pico，映射成一个更容易解释的 Maotuo：Pico 负责让模型完成任务，Maotuo 负责让模型在安全、可追踪、可恢复的边界内完成任务。

最重要的一句话：Maotuo 不是把 Pico 推倒重写，而是在 Pico 的 Agent Loop 外面增加了一层 Runtime 控制面，把“工具权限、文件证据、上下文预算、发布门禁、失败复盘和受控进化”统一纳入运行时管理。

1. 先用一句话理解 Maotuo

Pico 是什么

可以把 Pico 理解为一个轻量的模型工具循环：

用户问题→模型思考→调用工具→继续回答

重点是“模型能不能把任务做完”。

Maotuo 增加了什么

Maotuo 仍然保留这个循环，但在每一个关键边界加上治理：

谁能调用工具读到的文件是否仍然有效能否发布最终答案失败经验能否受控复用

重点变成“任务做完，而且过程可信、结果可审计”。

如果面试官只给我十秒钟，我会说：Maotuo 是基于 Pico 增量实现的轻量 Coding Agent Runtime。它不让模型直接拥有系统权限，而是让模型只提出计划和工具调用，再由 Runtime 完成权限校验、工具执行、证据校验和最终发布。

2. Pico 到 Maotuo：不要把它理解成换了一个项目

你已经了解 Pico，所以最有效的学习方式是看“原来的一步，现在由谁负责”。

原来 Pico 关注的事情Maotuo 的增量解决的真实问题
模型调用与工具循环AgentLoop + Maotuo.ask() 统一管理运行多轮任务有统一入口，能够记录、恢复和复盘。
模型可以提出工具调用ToolExecutor 和 Runtime 总闸口做白名单、参数、路径、审批校验模型的输出不等于系统的执行权限。
工具读写文件EvidenceStore 记录 SHA256，ReleaseGate 发布前检查 stale文件被外部修改后，不继续基于旧证据给出结论。
Prompt 逐渐变长ContextManager 做分层组装、裁剪和高价值上下文保护减少无效历史，同时保留当前请求和安全约束。
角色差异主要靠提示词RoleSkillManager 同时约束工具白名单并注入领域知识只读 Reviewer 从配置层就拿不到写工具。
失败后人工查看日志Trace、Audit、Report、Checkpoint 和 ReplayCase 形成失败闭环失败可以定位、恢复、回放，安全事件可审计。
提示词改进容易直接上线候选自动评测，人工审批，评测失败关闭自进化只改 Prompt 策略，不改工具权限和安全规则。
学习重点：Maotuo 的“核心逻辑”仍然是 Pico 的模型—工具循环；新增逻辑主要集中在入口、边界和持久化层。这样既保持轻量，也让安全能力能联动起来。

3. 总体架构：模型是决策者，Runtime 是执行裁判

下面这张图先只看方向，不要急着记文件名。上半部分是任务主路径，下半部分是围绕主路径的治理能力。

可以把模型想象成一名很聪明的工程师，把 Maotuo Runtime 想象成公司的代码仓库权限系统、发布系统和审计系统。工程师可以提出修改方案，但真正能不能读、能不能写、能不能发布，要由系统规则决定。

4. 运行时主循环：一次 ask() 到底发生什么

阅读代码时，先从 Maotuo.ask() 找到 AgentLoop.run()。所有能力最终都要回到这条主循环中。

1
创建本次 Run，并清理上一次运行的状态AgentLoop.run() 开始时重置发布门禁的重试计数，并通过 evidence_store.start_run(run_id) 做证据隔离。这样连续调用两次 ask() 时，第一次读过的文件不会污染第二次。
2
构造当前轮 PromptContextManager.build() 把 Role、Skill、当前请求、相关记忆、历史和高价值上下文组装起来；普通历史可以被裁剪，但硬约束优先保留。
3
调用模型并解析输出模型输出只能落到两个方向：提出一个结构化工具调用，或者提出最终答案。模型不是直接执行者。
4
工具调用必须过 Runtime 总闸口工具名、参数、路径、重复调用、审批策略和执行结果，都由 ToolExecutor 和 Runtime 统一处理。
5
最终答案必须过发布门禁如果证据中的文件 SHA256 与当前文件不一致，当前 final 被阻止；系统要求模型下一轮重新读取，最多重试两次。

5. 工具安全：模型只能“申请动作”，不能直接拥有动作

这是 Maotuo 最适合面试解释的安全边界。无论模型输出多么像一条命令，真正的执行都必须进入统一入口。

工具白名单

基础配置和 Role 共同决定当前运行可以看到哪些工具。Role 只能收缩权限，不能扩大基础安全边界。

消费者：模型提示和工具调用校验。
调用者：Maotuo 初始化、validate_tool()。

路径和参数

工具在真正执行之前检查参数格式、工作区边界、文件是否允许访问，避免把模型输出直接当成系统路径。

消费者：ToolExecutor。
调用者：AgentLoop 的每次工具循环。

审批和脱敏

高风险工具可以先进入审批策略；工具返回结果和报告写入前还要做敏感信息处理。

消费者：企业内网的操作安全和审计。
调用者：approve()、工具执行与报告生成流程。

6. 安全证据链：为什么每次工具执行后都要记录 SHA256

这里的关键词是 stale，中文可以理解为“证据过期”。Agent 读取文件后，文件可能被人、脚本或另一个进程修改；如果最终答案仍然基于旧内容，就会产生静默错误。

Run 隔离为什么重要：EvidenceStore.start_run(run_id) 会在新任务开始时切换 Run 并清理旧证据。否则第一次 ask() 读过的文件会被第二次任务错误地带入发布检查。
面试时我会这样说：我们没有把“文件内容”当成永久真相，而是把它当成某一次 Run、某一次工具执行时观察到的证据。最终发布前再次校验哈希，只有证据没有过期，答案才允许返回。

7. 上下文治理：不是尽可能塞多，而是把高价值信息放在前面

长任务的问题不是模型完全没有上下文，而是上下文中混入了重复读取、旧失败、普通历史和无关记忆。Maotuo 用 ContextManager 进行预算化组装。

为什么要合并重复读取

同一个文件被模型反复读取时，旧结果不断占用 Prompt，还会让模型误以为自己获得了新信息。Maotuo 将重复读取合并，减少无效 token。

为什么 Role/Skill 要保护

Role 是权限和身份边界，Skill 是当前领域知识。如果它们在普通裁剪中被截掉，模型可能忘记“我是谁”和“我能做什么”。

为什么失败信息要置顶

模型下一轮最需要知道的不是很久以前的完整对话，而是上一轮为什么失败、哪个文件 stale、下一步必须重读什么。

8. Role 与 Skill：一个管边界，一个管知识

对象它负责什么消费者是谁被谁调用
Role定义身份、基础提示和允许工具集合。Runtime 权限边界、模型上下文。Maotuo 初始化时读取；ContextManager 构造 Prompt 时注入。
Skill根据用户问题关键词匹配领域知识片段。模型的任务理解和执行指导。RoleSkillManager.active_skills() 被上下文构造流程调用。
filter_guidance()过滤与当前 Role 冲突的进化指导。只读角色的安全提示一致性。Maotuo._filtered_prompt_strategy() 在注入前调用。

9. 受控自进化：学习提示策略，不学习权限边界

Maotuo 的自进化不是“让模型自己改代码、自己扩大权限”，而是把失败转化成提示策略候选，再经过自动评测和人工审批。

评测失败默认不能激活：EvolutionStore.approve() 会检查 evaluation.approval_ready。未通过 GoldenTask / ReplayCase 门槛的候选，不能因为人工点了批准就进入 active。
我会把它解释为“提示策略的灰度发布系统”：失败先变成候选，候选先在封闭任务上验证，再由人批准。自进化可以改善模型怎么做事，但不能让模型获得原本没有的权限。

10. 运行工件：为什么要同时有 Trace、Audit、Report、Evidence、Checkpoint

这些文件不是重复保存同一份日志，而是服务不同消费者。理解这一点，你就能回答“审计和调试为什么要分开”。

工件记录什么主要消费者
trace.jsonl模型请求、工具调用、解析、状态变化、stale 等事件时间线。开发排障、失败复盘、Replay 抽取。
audit.jsonl权限拒绝、审批、高风险动作、stale、敏感信息等安全事件。安全审查、合规审计、事故调查。
report.json任务结果、结束原因、步数、失败摘要和运行统计。CLI 展示、评测汇总、简历数据整理。
evidence本次 Run 观察到的文件路径和 SHA256。ReleaseGate 的发布前校验。
checkpoint可恢复的任务状态和关键上下文。中断恢复、失败重放、任务继续执行。

11. 模块地图：每个模块给自己问三句话

你之前提出的约束非常适合用来读代码：它做什么？消费者是谁？它被谁调用？

模块 / 文件一句话职责消费者是谁被谁调用
maotuo/cli.py命令行入口，加载配置并启动一次任务。开发者、部署运维人员。用户命令；内部创建 Maotuo。
maotuo/runtime.pyRuntime 总装配和安全总闸口。AgentLoop、模型、工具执行流程。cli.py 或调用方通过 Maotuo.ask()；循环中调用 run_tool()、check_release_gate()。
maotuo/agent_loop.py编排一轮轮“构造 Prompt→请求模型→工具或 final”。一次 Coding 任务的完成结果。Maotuo.ask() 调用 AgentLoop.run()。
maotuo/context_manager.py按预算组装、保护和裁剪上下文。模型客户端的输入 Prompt。AgentLoop.run() 每次模型请求前调用 build()。
maotuo/tool_executor.py统一执行工具，承接校验、审批、执行和结果记录。文件工具、受限 Shell、证据和 Trace。AgentLoop 和 Runtime 的工具执行入口。

maotuo/role_skill.py提供 Role 权限和 Skill 领域提示。工具白名单和 ContextManager。Runtime 初始化、上下文构造、进化指导注入前过滤。
maotuo/evolution.py保存失败信号、候选、评测结果和审批状态。受控 Prompt 策略治理。AgentLoop 失败处理、Runtime 信号记录、CLI 审批。
maotuo/evaluation/replay.py运行 GoldenTask，抽取和回放 ReplayCase。候选评测和失败复盘。EvolutionStore.create_candidate() 与评测命令。
maotuo/checkpoint.py保存任务状态，让任务可恢复。恢复执行和失败分析。AgentLoop 在工具执行、失败、成功等关键节点调用。
maotuo/run_store.py管理每次 Run 的目录、Trace、Report 等持久化位置。运行记录、评测和审计系统。Runtime / AgentLoop 初始化和结束流程。

12. 面试或汇报逐字稿

下面可以直接照着讲。括号里的内容是你可以根据面试官追问展开的方向，不需要全部背。

逐字稿一：一分钟介绍项目
我做的是 Maotuo，一个基于 Pico 增量实现的轻量级、安全可审计的垂类 Coding Agent Runtime。它面向企业内网代码审查、测试修复和受控修改场景。Pico 原本已经具备模型和工具的基本循环，Maotuo 在这个循环外增加了 Runtime 控制面：模型只能提出工具调用，工具白名单、路径校验、审批、文件证据和最终发布都由 Runtime 控制。这样做主要是为了解决 Coding Agent 在真实仓库里最危险的几个问题：模型可能使用越权工具，文件在读取后可能被外部修改，Prompt 可能因为长任务不断膨胀，失败经验也可能未经验证就被重新使用。Maotuo 用 Role/Skill 做垂类定制，用 Evidence 和 ReleaseGate 防止过期证据发布，用 Trace、Audit 和 Checkpoint 支持审计与恢复，再用 GoldenTask、ReplayCase 和人工审批形成受控自进化闭环。
逐字稿二：从用户请求到最终答案
一次请求从 Maotuo.ask() 进入 AgentLoop.run()。运行时先创建一个独立的 Run，并清理上一轮的发布状态和证据。然后 ContextManager 根据当前 Role、Skill、当前请求、相关记忆、历史消息和失败信息组装 Prompt。模型返回后，Runtime 会把结果解析成工具调用或者最终答案。如果是工具调用，它必须通过工具白名单、参数和路径检查，必要时还要经过审批，之后才由 ToolExecutor 执行。工具执行结束后，涉及的文件会记录 SHA256，并把事件写进 Trace。模型继续下一轮。如果模型给出 final，Maotuo 不会直接返回，而是先由 ReleaseGate 重新检查文件哈希。如果发现文件被修改，就阻止当前 final，把“文件可能过期，请重新读取”反馈到下一轮 Prompt，最多重试两次。只有通过发布门禁，答案才会被保存并返回。
逐字稿三：为什么不能让模型直接执行工具
模型适合做决策和规划，但模型输出本质上是不可信的文本。它可能生成错误路径、调用不适合当前角色的工具，或者在不知道文件已经变化的情况下继续作答。所以 Maotuo 把模型和系统副作用分开：模型只能输出结构化的工具申请，Runtime 通过统一入口检查工具白名单、参数、路径、重复调用和审批策略，然后才执行。这个设计的好处是，即使模型提示被误解或者模型产生幻觉，安全边界仍然在 Runtime，而不是依赖模型“自觉遵守”。
逐字稿四：如果文件在读取后被改了怎么办
每次工具执行后，Maotuo 会对涉及文件计算 SHA256，并把路径、哈希和当前 Run 关联起来。最终答案发布前，ReleaseGate 会重新计算这些文件的哈希。如果哈希变化，说明 Agent 看到的证据已经过期，当前 final 会被阻止。系统会写入 stale 事件，并在下一轮 Prompt 中明确告诉模型哪些文件可能过期、需要重新读取。这个过程最多重试两次；如果仍然无法获得稳定证据，任务终止并生成失败信号和 ReplayCase。也就是说，stale 不是标记一下，而是会触发重读、阻止发布、限次重试、失败沉淀的一整条链路。
逐字稿五：Role 和 Skill 有什么区别
Role 解决的是“我是谁，以及我能做什么”。例如只读 Reviewer 的 Role 可以只开放读取、搜索和测试工具，不开放写文件工具。Skill 解决的是“我掌握什么领域知识”，比如安全审查 Skill 可以注入敏感信息、越权路径和测试验证方面的提示。Role 同时参与权限收缩和 Prompt 保护，Skill 主要根据用户请求的关键词匹配后注入领域片段。即使某个自进化策略建议使用写工具，在注入前也要经过当前 Role 过滤，所以只读角色不会因为提示策略而获得写权限。
逐字稿六：受控自进化如何避免失控
Maotuo 的自进化只针对 Prompt 策略，不改工具白名单、不改路径校验、不改审批规则和 ReleaseGate。任务失败或 stale 会产生结构化信号，系统据此生成候选提示策略。候选生成后会自动运行 GoldenTask 和 ReplayCase，评测结果会附加到候选上。只有评测达到门槛、并且人工审批通过，候选才会成为 active 策略；如果评测失败，审批接口会 fail-closed，不能强行激活。真正注入下一次 Prompt 前，策略还要经过当前 Role 过滤。这相当于一个轻量的提示策略发布流程，而不是让 Agent 自己修改自己的安全底座。
逐字稿七：为什么不引入 LangChain
这个项目的目标是做一个轻量、可审计、适合企业内网部署的 Runtime。当前核心需求是模型客户端、工具执行、上下文管理、证据校验、状态持久化和评测闭环，这些能力在现有 Python 代码上可以直接实现。如果引入更大的框架，会增加抽象层、依赖和排障成本，也不一定能自动满足我们的安全边界。所以我选择保留 Pico 的轻量循环，通过模块化的增量代码实现能力，并用 pytest、GoldenTask、ReplayCase 和真实模型评测验证行为。
逐字稿八：怎么证明它真的有效
我把验证分成三层。第一层是确定性的安全回归，包括路径越界、审批边界、stale 发布阻断和敏感信息脱敏，当前 GoldenTask 为 4/4。第二层是上下文和运行时压力实验，观察 Prompt 压缩、重复读取、当前请求保留率和预算完成率。第三层是真实模型消融评测，在相同任务、模型和解码条件下比较 Baseline、Prompt Only、Prompt + Context 和 Full，区分功能收益与安全收益。这样不是只看最终通过率，而是同时看安全事件有没有被阻断、Prompt 是否变短、任务是否在预算内完成、失败是否能回放。

面试官追问时的核心回答

追问建议回答关键词
Maotuo 和 Pico 的关系？保留 Pico 的轻量 Agent Loop；Maotuo 是增量 Runtime 控制面，不是重写模型能力。
最核心的安全点？模型不直接执行；工具统一过 Runtime；文件证据按 Run 隔离；final 需要 ReleaseGate。
为什么要 SHA256？把“我读到的文件”变成可验证证据，检测读取后是否被改。
stale 后只是重试吗？不是：写 Trace/Audit、阻止 final、反馈重读、最多两次，失败后进化信号和 Replay。
自进化会不会扩大权限？不会；只改 Prompt 策略，工具权限和安全规则固定；候选自动评测、人工审批、Role 过滤。
如何恢复任务？Checkpoint 保存状态；Trace 复盘过程；ReplayCase 把失败场景变成可回归案例。

14. 建议的代码阅读路线

不要从所有文件平铺阅读。按照下面顺序，你可以把 Pico 的旧知识逐步映射到 Maotuo 的新增能力。

1
先看入口：maotuo/runtime.py重点看 class Maotuo、ask()、run_tool()、check_release_gate()。先理解 Runtime 负责装配什么，以及它在哪里拦截动作。
2
再看主循环：maotuo/agent_loop.py重点看 run()、_request_model()、_check_final_gate()、_finish_success()。把一次任务按“创建 Run、请求模型、工具分支、final 分支”画出来。
3
理解工具边界：maotuo/tool_executor.py、maotuo/tools.py、maotuo/security.py确认模型输出怎样变成工具调用，以及路径校验、审批、脱敏在哪里发生。
4
理解 stale：maotuo/evidence.py看 observe()、observe_tool()、stale() 和 ReleaseGate.check()，再回到 AgentLoop._check_final_gate() 看失败如何反馈给模型。
5
理解 Prompt：maotuo/context_manager.py、maotuo/role_skill.py关注 Role/Skill 如何进入 Prompt，高价值上下文如何置顶，普通历史怎样被裁剪。
6
最后看闭环：maotuo/evolution.py、maotuo/evaluation/replay.py、maotuo/checkpoint.py理解失败如何进入信号、候选、评测、审批、激活和 Replay；这部分是 Maotuo 从“能跑”走向“可治理”的关键。
